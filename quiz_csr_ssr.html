🖥️ Quiz — CSR vs SSR

Question 1

Vrai ou Faux

Dans le rendu côté client, le serveur retourne une page HTML complète avec toutes les données déjà insérées.

👁️ Voir la réponse

✅ FAUX

Dans le CSR, le serveur envoie une page quasi vide. C'est ensuite le navigateur qui, via des appels API, récupère les données et génère le HTML dynamiquement côté client.

Question 2

Choix multiple

Lequel des énoncés suivants décrit le mieux le rendu côté serveur (SSR) ?

  • A) Le navigateur télécharge du JavaScript et génère le HTML lui-même
  • B) Le serveur génère un HTML complet et l'envoie directement au navigateur
  • C) Le serveur envoie une page vide et le client fait des appels API pour obtenir les données
  • D) Le rendu se fait en WASM directement dans le navigateur
👁️ Voir la réponse

✅ B) Le serveur génère un HTML complet et l'envoie directement au navigateur

  • A) ❌ C'est le CSR
  • C) ❌ C'est le CSR
  • D) ❌ WASM peut être utilisé en CSR, mais ce n'est pas la définition du SSR

Question 3

Court développement

Pourquoi le rendu côté serveur est-il généralement meilleur pour le référencement (SEO) comparé au rendu côté client ?

👁️ Voir la réponse

Éléments de réponse attendus :

  • Les robots des moteurs de recherche (ex. : Googlebot) lisent le HTML directement
  • En SSR, le HTML est déjà complet à la réception → le robot peut l'indexer immédiatement
  • En CSR, la page est quasi vide à la réception → le robot doit exécuter le JavaScript pour voir le contenu, ce qu'il ne fait pas toujours correctement

Question 4

Choix multiple

Dans une application en rendu côté client, quel est le rôle principal du serveur ?

  • A) Générer le HTML final et l'envoyer au client
  • B) Exécuter le JavaScript pour préparer la page
  • C) Fournir des données via des appels API
  • D) Compiler le code WASM à la demande
👁️ Voir la réponse

✅ C) Fournir des données via des appels API

  • A) ❌ C'est le rôle du serveur en SSR
  • B) ❌ Le JavaScript est exécuté dans le navigateur, pas sur le serveur
  • D) ❌ WASM est compilé à l'avance, pas à la demande

Question 6

Vrai ou Faux

Une application en rendu côté serveur ne peut jamais avoir des interactions fluides sans rechargement de page.

👁️ Voir la réponse

✅ FAUX

Il est possible de pallier cette lacune via des librairies comme htmx, qui permettent de faire des mises à jour partielles de la page sans rechargement complet, tout en conservant le SSR.

Question 7

Court développement

Ton patron te demande de développer un site vitrine pour une boutique en ligne. Le référencement Google est une priorité absolue. Quelle approche de rendu recommanderais-tu et pourquoi ?

👁️ Voir la réponse

✅ SSR (rendu côté serveur)

  • Le référencement Google est prioritaire → le HTML doit être lisible immédiatement par les robots
  • Un site vitrine nécessite peu d'interactions complexes → les rechargements de page ne sont pas un problème majeur
  • Le SSR est simple et efficace pour ce type d'usage

  • D) Angular ❌ — framework CSR

Question 9

Court développement

Nomme une situation où le rendu côté client serait un meilleur choix que le rendu côté serveur. Justifie ta réponse.

👁️ Voir la réponse

Exemples de réponses acceptables :

  • Un tableau de bord (dashboard) avec graphiques mis à jour en temps réel
  • Une application interne d'entreprise où le SEO n'a aucune importance
  • Une application de messagerie (type Slack, Teams) nécessitant une grande réactivité
  • Une application mobile-first de type SPA

Justification attendue : le SEO n'est pas une priorité ET la réactivité de l'interface est importante.

Question 10

Analyse

Un développeur dit : "Je préfère toujours utiliser le rendu côté client, c'est plus moderne et plus performant."

Identifie deux faiblesses dans cet argument en te basant sur ce que tu as appris.

👁️ Voir la réponse

Deux faiblesses parmi les suivantes :

  • « Plus performant » est relatif : en CSR, le premier chargement est souvent plus lent car le navigateur doit télécharger le JavaScript, l'exécuter et faire des appels API avant d'afficher quoi que ce soit
  • Mauvais pour le SEO : les moteurs de recherche ont du mal à indexer du contenu généré dynamiquement par JavaScript
  • Complexité accrue : le CSR nécessite une logique côté client ET une logique côté serveur (API), ce qui augmente la complexité du projet
  • « Plus moderne » n'est pas un argument technique : le choix doit dépendre des besoins du projet, pas de la tendance
